# Система учёта инцидентов информационной безопасности (MVP)

Прототип системы регистрации, разбора и контроля сроков реагирования на инциденты информационной безопасности (ИБ) для строительной компании (250 сотрудников, 180 рабочих станций). Реализует сквозной цикл управления инцидентом: от приёма первичного сигнала и дедупликации до работы по чек-листу, контроля сроков Роскомнадзора (РКН), 30-минутной эскалации и месячной отчётности.

## Технологический стек

- **Backend**: Python 3.13, FastAPI, Uvicorn, менеджер пакетов `uv`
- **База данных**: SQLite (встроенный модуль `sqlite3`, без ORM)
- **Frontend**: React 19, Vite 6 (SPA на русском языке, прокси `/api` -> `http://127.0.0.1:8000`, печать отчёта в PDF через `@media print`)
- **Тестирование**: `fastapi.testclient.TestClient` (`httpx`) в [test_e2e.py](test_e2e.py)

## Как устроена внутрянка

### Архитектура и структура файлов

- [main.py](main.py) — точка входа FastAPI, инициализация БД при старте (`lifespan`), подключение роутеров.
- [db.py](db.py) — схема SQLite (9 таблиц) и сидирование тестовых данных при первом запуске:
  - `users` — учётные записи для 4 ролей (`ib_specialist`, `sysadmin`, `it_head`, `lawyer`).
  - `sessions` — токен-сессии (`Authorization: Bearer <token>`).
  - `incidents` — карточки инцидентов (статусы: `Новый`, `В работе`, `На проверке`, `Закрыт`; критичность: `low`, `medium`, `high`, `critical`; отметка ПДн `has_personal_data`; временные метки `detected_at`, `taken_at`, `closed_at`; черновик РКН `rkn_draft`).
  - `messages` — входящие сигналы, привязанные к карточке.
  - `history` — аудит-журнал всех действий по карточке.
  - `instructions` — 4 предзаполненных шаблона пошаговых инструкций реагирования.
  - `step_progress` — отметки выполнения шагов инструкции по конкретному инциденту.
  - `tasks` — задачи исполнителям (например, системному администратору) и результат выполнения.
  - `notifications` — журнал эскалаций и срочных оповещений.
- [auth.py](auth.py) — локальная аутентификация (`POST /api/auth/login`, `GET /api/auth/me`), хэширование паролей через `sha256` и проверка Bearer-токена (`get_current_user`).
- [routers/incidents.py](routers/incidents.py) — CRUD инцидентов, поиск и фильтрация, переходы статусов с фиксацией `taken_at` / `closed_at`, запись в `history` и приём внешних сигналов (`POST /api/signals`).
- [routers/ops.py](routers/ops.py) — инструкции и прогресс шагов, задачи, расчёт сроков РКН и черновик уведомления, проверка 30-минутной эскалации, журнал уведомлений и месячный отчёт.
- [frontend/](frontend/) — клиентское SPA-приложение:
  - [frontend/src/api.js](frontend/src/api.js) — клиент REST API с хранением токена в `localStorage`.
  - [frontend/src/pages/IncidentsPage.jsx](frontend/src/pages/IncidentsPage.jsx) — реестр инцидентов, фильтры, поиск, ручная регистрация, индикация просрочек.
  - [frontend/src/pages/IncidentDetailPage.jsx](frontend/src/pages/IncidentDetailPage.jsx) — карточка инцидента, смена статуса, чек-лист инструкций, задачи, таймеры РКН (24 ч / 72 ч) и редактирование черновика, лента сообщений и истории.
  - [frontend/src/pages/TasksPage.jsx](frontend/src/pages/TasksPage.jsx) — «Мои задачи» с фиксацией результата.
  - [frontend/src/pages/SimulatorPage.jsx](frontend/src/pages/SimulatorPage.jsx) — эмулятор сигналов от Kaspersky, Zabbix, почты и Telegram.
  - [frontend/src/pages/NotificationsPage.jsx](frontend/src/pages/NotificationsPage.jsx) — журнал уведомлений и запуск проверки просрочек.
  - [frontend/src/pages/ReportPage.jsx](frontend/src/pages/ReportPage.jsx) — месячный отчёт и экспорт в PDF.

### Ключевые механизмы

1. **Ролевой доступ (RBAC)**: роль `sysadmin` не видит инциденты с `has_personal_data = 1` в списке инцидентов и списке задач, а при прямом обращении к таким карточкам, шагам, задачам или разделу РКН получает `403 Forbidden`.
2. **Дедупликация сигналов** (`POST /api/signals`): при поступлении сигнала система ищет открытый инцидент (`status != 'Закрыт'`) по `incident_key` либо по паре `(computer, incident_type)`. При совпадении сообщение прикрепляется к существующей карточке без создания дубля.
3. **Контроль сроков РКН**: для инцидента вычисляются крайние сроки первичного (`detected_at + 24ч`) и дополнительного (`detected_at + 72ч`) уведомлений, флаги просрочки и формируется редактируемый черновик уведомления в Роскомнадзор.
4. **30-минутная эскалация и оповещения** (`POST /api/escalations/check`): не взятые в работу (`status == 'Новый'`, `taken_at IS NULL`) инциденты старше 30 минут порождают эскалацию руководителю ИТ-отдела (`it_head`), а открытые инциденты с ПДн — адресные уведомления юристу (`lawyer`) и главному бухгалтеру (`chief_accountant`) без дублирования.
5. **Месячный отчёт** (`GET /api/reports/monthly`): агрегирует уникальные карточки инцидентов за выбранный месяц по типам, статусам, итогам проверки и критичности (без дублирования повторных сигналов).

## Запуск проекта

### 1. Backend (API)

```powershell
uv sync
uv run uvicorn main:app --reload
```

Сервер запустится на `http://127.0.0.1:8000` (Swagger UI доступен на `/docs`). База `incidents.db` создаётся и заполняется автоматически при первом старте.

### 2. Frontend (SPA)

Во втором терминале:

```powershell
cd frontend
npm install
npm run dev
```

Веб-интерфейс откроется на `http://localhost:5173`. Запросы к `/api/*` автоматически проксируются на `http://127.0.0.1:8000`.

### 3. Проверка сквозных сценариев (E2E)

```powershell
uv run python test_e2e.py
```

Скрипт проверяет на изолированной временной БД все 4 приёмочных сценария: дедупликацию сигналов, работу по инструкции с RBAC для ПДн, сроки РКН и 30-минутную эскалацию, а также агрегацию месячного отчёта.
